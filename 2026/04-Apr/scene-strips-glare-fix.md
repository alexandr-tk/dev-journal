# Fixing Scene Strips Not Preserving Glare from Compositor on Alpha Over

**The Result:** [PR #157028](https://projects.blender.org/blender/blender/pulls/157028)

## 1. Workflow

- **Task:** Identify why luminous pixels (glare) generated by the compositor disappear in the Video Sequence Editor (VSE) when placed over another strip, and implement a fix.
- **Issue Link:** [Issue #156235](https://projects.blender.org/blender/blender/issues/156235)
- **Reasoning:**
    - Deepen understanding of Blender's internal image buffer (`ImBuf`) handoff between the rendering pipeline and the VSE.
    - Resolve a core compositing discrepancy involving premultiplied alpha math and fast-path optimizations.

## 2. Context

This bug involves the data flow from the 3D Scene through the Compositor to the Video Sequence Editor (VSE). The pipeline works as follows:

1. **The 3D Scene:** We have an emitting object against a transparent background (`Film -> Transparent` enabled).
2. **The Compositor:** The Glare node takes the bright pixels of the emitting object and smears them outward to create a glow.
3. **The VSE:** The resulting image is placed on the timeline as a Scene Strip.

The root of the issue lies in how Alpha Channels are handled in VFX. When we apply a glare node against a transparent background, it generates pixels that have color (energy) but no physical opacity ($A = 0$). These are referred to as **luminous/emissive pixels** ($RGB > 0$, $A = 0$).

When blending that final result with a solid background strip, the glare completely disappears instead of projecting its light onto the background.

## 3. Problem Core

The VSE blends stacked strips from top to bottom. The properties of this blending are determined by the Blend Mode (usually "Alpha Over").

In industry-standard VFX compositing, render engines output **Premultiplied Alpha**. This means the RGB channels have already been mathematically multiplied by the alpha channel to prevent dark fringes around anti-aliased edges.

The standard Alpha Over math for premultiplied images is:
$C_{final} = C_{top} + C_{bottom} \times (1 - \alpha_{top})$

If we evaluate our luminous glare pixel where the top strip is bright ($C_{top} = 1$) but has no opacity ($\alpha_{top} = 0$), the math becomes:
$C_{final} = 1 + C_{bottom} \times (1 - 0)$
$C_{final} = 1 + C_{bottom}$

Mathematically, this results in a perfect **Additive Blend**. The glare should be perfectly preserved and shine over the background. Because the glare was vanishing, it indicated that the VSE was fundamentally altering or discarding the $C_{top}$ value before the blending formula could execute.

## 4. Plan for Solving

My initial theory was an "Amnesia Bug" during the module handoff. I hypothesized that when the VSE requested an image buffer from the scene, it was failing to flag the buffer as `IMA_ALPHA_PREMUL`.

1. Investigate the `add_scene_strip` initialization and `add_image_init_alpha_mode` to see how alpha flags are set.
2. If flags are correct, track the buffer into the VSE's blending execution (`effect_blend.cc`) to find where the RGB values of the luminous pixels are being crushed.
3. Formulate a C++ patch to preserve the math.

## 5. Solving the Issue

### Attempt 1: The Initialization Flag (Red Herring)

I first looked into how strips initialize their alpha states. For standard Image Strips, Blender checks the file metadata:

```cpp
      strip->alpha_mode = SEQ_ALPHA_STRAIGHT;
      if (ibuf) {
        if (ibuf->flags & IB_alphamode_premul) {
          strip->alpha_mode = IMA_ALPHA_PREMUL;
        }
      }
```

I noticed `add_scene_strip` completely bypassed this explicit `alpha_mode` assignment, leaving it to default to `SEQ_ALPHA_STRAIGHT`. I initially thought forcing `strip->alpha_mode = IMA_ALPHA_PREMUL` here would solve it. However, after further codebase tracing, I discovered that the VSE doesn't actually read `strip->alpha_mode` when executing the render stack for Scene Strips. The bug had to be in the blending engine itself.

### Attempt 2: The Fast-Path Optimization Trap

I moved my investigation to `effect_blend.cc`, the engine room for VSE pixel math. Here, I found the true culprit—a flawed performance optimization for the Alpha Over effect:

```cpp
      if (src1[3] <= 0.0f) {
        /* Alpha of zero. No color addition will happen as the colors are pre-multiplied. */
        memcpy(dst, src2, sizeof(T) * 4);
      }
```

In this pixel array, `src1[3]` represents the Alpha channel of the top strip. The original developer wrote this to save CPU cycles: if a pixel is fully transparent, skip the heavy blending math and just copy (`memcpy`) the background pixel directly to the screen.

**The Fatal Flaw:** The developer assumed a 2D graphics logic ($A = 0$ means the pixel is completely empty). They forgot about VFX emissive pixels. A glare pixel has $A = 0$, but $RGB > 0$. When the VSE hit the glare, this `if` statement triggered, blindly discarding the valid RGB light data and replacing it with the solid background color.

### Implementing the Fix

To fix this without destroying the performance optimization for truly empty space, the condition needed to verify that the pixel emits _no light_ and has _no opacity_.

I updated the condition to check all four channels (`R, G, B, A`):

```cpp
      if (src1[0] <= 0.0f && src1[1] <= 0.0f && src1[2] <= 0.0f && src1[3] <= 0.0f) {
        /* Pixel emits no light and has no opacity. Safe to optimize. */
        memcpy(dst, src2, sizeof(T) * 4);
      }
```

With this change, when the playhead hits the glare pixel, it sees that while Alpha is $0.0$, the Red channel might be $1.0$. The fast-path fails, forcing the VSE to send the pixel through the actual Alpha Over math loop, which cleanly adds the light to the background.

## 6. Testing

I compiled the build and recreated the specific bug conditions. The fix worked flawlessly: the glare survived the VSE blend.

## 7. Conclusion

By modifying the `memcpy` fast-path in `effect_blend.cc` to evaluate RGB values alongside Alpha, the Sequencer now correctly respects additive VFX data generated by the 3D pipeline and Compositor, while maintaining its optimization for empty space.
